# Roadmap: "Are we on track?"

Date: 2026-11-18
Status: Planned
Issues: one per phase (see [Phases](#phases)), plus an optional backlog clean-up

## Problem

Goals today are checked one at a time. Each `GoalCard` shows On Track or Behind against its own deposit pace (`getGoalPacing`). Nothing answers the household question: **can we afford all our goals together** (wedding, house, children) on what we actually save, and what changes when life events alter the monthly budget?

## Decisions (settled with the user; do not reopen)

### Model

1. **Goals are claims on one household pool, not tied to accounts.** Money moves freely between accounts, so goals are account-agnostic.
2. **Pool** = all non-CPF account balances (Cash, Investment, Other), minus unpaid card statements. This is the same definition as net worth in [card-debt-net-worth](2026-11-04-card-debt-net-worth.md). It is valued **as of the last balance update** ("Updated 12 days ago"), and the projection starts from that date. There is no per-account "count in pool" toggle.
3. **Investment haircut:** investments count at a discount for goals due inside a window. The defaults are **80% within 24 months** and full value beyond that. Both numbers become household settings in Phase 4. Future savings are treated as cash. There is no "how much to sell" feature.
4. **Goal progress is computed, not deposited.**
    - The pool is shared out in **date order only**: the buffer first, then each goal filled to 100% before the next.
    - Ties are broken by `created_at`. There is no manual priority or pinning.
5. **Still needed** = target − goal-tagged spending so far (expenses with `goal_id`). This stops early deposits, such as a venue deposit, from making a goal look worse.
6. **Done:** marking a goal Done (`status = "achieved"`) takes it out of the order of goals. A goal past its date that isn't Done shows "Paid for? Mark done".
7. **Retired:**
    - Quick deposit, the month-end surplus sweep into goals, and the bonus-split-to-goals step all go. The bonus log stays.
    - `saved_so_far` and `goal_deposits` are left in the DB but no longer read. Dropping them is an optional backlog item.
8. **One shared household plan.** The Roadmap ignores the perspective switch and shows a "Household plan" label. Personal goals count against the shared pool.

### Baseline (what we save per month)

9. **Monthly savings** = allocation-category amounts (`group: "allocation"`) + spendable underspend (the `delta` from `calculateCumulativeSurplus`). It is averaged over the last 3–6 months and **excludes bonuses** (`MonthlyBudget.bonus`).
    - The existing "surplus" alone is underspend against the spending budget, not savings, and must not be used on its own.
    - With fewer than 3 months of history, fall back to budgeted savings, labelled "Estimate".
10. **Bonuses** appear only as an optional "with typical bonus" trade-off. The plan must work on salary alone.

### Verdict engine

11. **Deadline check, not a month-by-month simulation.** Sort goals by date. At each goal's deadline `d`:
    `pool(d) + savings until d (± dated cash-flow changes) ≥ still-needed of this goal and every earlier one`.
    - **Verdict:** the worst gap across deadlines, or the smallest spare margin if nothing is short.
    - **Shortfall per month:** the largest gap ÷ months until that deadline.
12. **Life events** are dated cash-flow changes (future recurring items, e.g. childcare, mortgage, rent ending). A change only applies to **future** months, and stops being added once the baseline window covers its start date, so it is never counted twice.
13. **Trade-offs are scenarios:** `projectRoadmap(input, scenario)`, where a scenario is a list of edits.
    - Each trade-off shows one action and one result: "Delay House 8 mo → On track".
    - **Applying a trade-off changes the goal straight away.**
    - The available trade-offs are Delay, Lower target, Trim category (picked from actual spending headroom) and +Bonus.
14. **One source of truth.** Verdict, Pool Jar, tap-to-preview, timeline, Dashboard chip and alerts all read `projectRoadmap` output.

### CPF

15. **Exactly three CPF accounts per member: OA, SA and MA.**
    - They are created automatically, with a structured `cpf_kind` instead of matching on the name (today: `BulkBalanceUpdateModal.tsx:115`).
    - You can't add or delete CPF accounts by hand. The migration matches existing accounts by name and shows any it can't match.
16. **SA and MA never fund goals in v1**; they count in net worth only.
17. **"Use CPF OA" goal switch** (off by default) with an optional **"up to $X" cap**.
    - The cap covers private property and other limits. Bubby does not encode CPF rules; it links to CPF's own calculator.
    - A goal with the switch on is funded from household OA first (all members combined), then from the pool.
18. **OA growth** is the average from the last 3+ OA snapshots. Before that, use today's balance with no growth.
19. **"Paid from CPF OA"** on a recurring item (the mortgage) reduces OA growth from its start date instead of cash savings.
    - The Loans tab is a placeholder today (`src/components/loans/LoansPlaceholder.tsx`), so the mortgage is a recurring item.
    - A rebuilt Loans feature should reuse the same fields.

### Goals

20. **Tags:** free-form, with suggestions seeded from Wedding, Housing, Child, Education, Travel and Car. A tag sets the default emoji and template label only. **Tags carry no rules**, so there is no tag management screen.
21. **Buffer goal type:** one per household.
    - Its target is N months of average spending, snapshotted when set, with a "Refresh target" action.
    - It is always funded first.
22. **Templates** set labels only. They never prefill amounts, which would go stale and could read as financial advice.
23. **Linked costs:** a recurring item can be linked to a goal with an offset ("at goal date", "+9 months"). Delaying the goal moves it.

### UI

24. **Placement:** Roadmap at the top of Plan → Goals (verdict + Pool Jar + timeline), plus a Dashboard text chip ("On track" or "Short $400/mo").
25. **Pool Jar:**
    - **Look:** a rounded jar (`border-2`, `shadow-cute`, `--pastel-*` water, light and dark).
    - **Goal bands:** stacked from the bottom in funding order, sized by target with a minimum height (`min-h-11`). A very large goal gets a squiggle break. Emoji ticks and `TruncatedText` labels sit on the side, funded bands get a ✓, and the water line is marked "you are here".
    - **Tap a band** to animate the water to its projected level on that goal's date, showing "Fills by May 2028 ✓" or "Short $6k". Tap again to return to today.
    - **Haircut:** not drawn. Today's level uses the **discounted** pool, a preview of a goal outside the window uses full value, and a tooltip on the total explains it.
    - **Motion:** fills once on first view and ripples when the level changes. `transform`/`opacity` only, presets from `src/lib/motion.ts`, static under reduced motion.
    - **Accessibility:** `role="img"` with a summary label, plus a band list beneath it for screen readers.
    - Respects masked money (`src/lib/maskMoney.ts`). Empty state: "No goals" with one prompt and an "Add goal" button.
26. **Net worth reality check** (Phase 2):
    - **Check:** a second line under the verdict: "Balances grew $X/mo vs budget $Y/mo".
    - **Warning:** shown when the two differ by more than ~20%.
    - **Excluded months:** months with goal-tagged spending (`goalSpent > 0`) are left out.
    - **Projection chart:** solid history continuing as a dashed projection. It dips at each milestone payment and life events change its slope. No investment-return assumptions.
    - **Unlock:** needs 3+ monthly snapshots, with gaps filled by straight lines. Before that, "Update balances monthly to unlock".
27. **Alerts:** `goal_pacing` fires only when a goal's status changes (on track ↔ short). It is checked once after each balance update, at most one alert per goal per month, and reuses the existing `goal_pacing_alerts` preference.

### DB changes (the user runs these; drafts, check against the schema before running)

Phase 3:

```sql
alter table accounts add column if not exists cpf_kind text
    check (cpf_kind in ('OA', 'SA', 'MA'));
update accounts set cpf_kind = case
    when name ~* '\mOA\M' or name ~* 'ordinary' then 'OA'
    when name ~* '\mMA\M' or name ~* 'medi' then 'MA'
    when name ~* '\mSA\M' or name ~* 'special' then 'SA'
end
where type = 'CPF' and cpf_kind is null;
-- Review rows still null before adding the constraint.
create unique index if not exists accounts_owner_cpf_kind_key
    on accounts (owner_id, cpf_kind) where cpf_kind is not null;

alter table savings_goals
    add column if not exists use_cpf_oa boolean not null default false,
    add column if not exists cpf_oa_cap numeric(12, 2);
alter table recurring_items
    add column if not exists paid_from_cpf_oa boolean not null default false;
```

Phase 4:

```sql
alter table savings_goals
    add column if not exists tags text[] not null default '{}',
    add column if not exists goal_type text not null default 'standard'
        check (goal_type in ('standard', 'buffer')),
    add column if not exists buffer_months integer
        check (buffer_months between 1 and 24);
create unique index if not exists savings_goals_one_buffer_key
    on savings_goals (household_id) where goal_type = 'buffer';
alter table households
    add column if not exists investment_haircut_pct numeric(5, 2) not null default 20,
    add column if not exists investment_haircut_months integer not null default 24;
```

Phase 5:

```sql
alter table recurring_items
    add column if not exists goal_id uuid references savings_goals (id) on delete set null,
    add column if not exists goal_offset_months integer;
```

Backlog (optional, can't be undone):

```sql
drop table if exists goal_deposits;
drop table if exists bonus_goal_contributions;
alter table savings_goals drop column if exists saved_so_far;
```

## Out of scope (v1)

- Investment returns, inflation and salary growth.
- Selling or liquidity advice.
- CPF valuation and withdrawal limits (the user sets the cap).
- SA/MA for goals.
- Per-member pools.
- Manual goal priority.
- The Loans rebuild.
